# Лекция 1: `self`/`&self`, `Option`, borrow checker и паника vs `Result`

Конспект по вопросам, которые возникли при написании `IsDayOffBuilder` и
`build_url` в этом проекте. Примеры — реальный код из `src/client.rs`.

---

## 1. `self` vs `&self` vs `&mut self`

У методов в Rust три варианта первого параметра — и это не формальность,
а вопрос **владения (ownership)**.

- **`&self`** — метод берёт объект по неизменяемой ссылке (borrow). Читает
  поля, объект остаётся у вызывающего кода и им можно пользоваться дальше.
- **`&mut self`** — то же, но с правом изменять поля.
- **`self`** — метод **забирает объект по значению** (consuming/move).
  После вызова исходная переменная перестаёт существовать — компилятор не
  даст ей воспользоваться.

### Почему это вообще ошибка компиляции, а не рантайм-баг

```rust
fn build_url(self, year: i32, month: Option<u32>, day: Option<u32>) -> String {
    // ...
}
```

Вызов `client.build_url(...)` **поглощает** `client`. Дальше нельзя написать:

```rust
let url = self.build_url(...);       // self "съеден"
self.http.get(&url).send().await?;   // ОШИБКА: self уже перемещён (moved)
```

потому что `build_url` требовал владение целиком, а не просто заглядывал в
поля. А нам внутри `day()`/`month()` нужно и построить URL из полей `self`,
и следом ещё раз использовать `self.http` — то есть метод должен только
**посмотреть** на данные. Поэтому правильная сигнатура:

```rust
fn build_url(&self, year: i32, month: Option<u32>, day: Option<u32>) -> String {
```

**Правило по умолчанию:** если методу не нужно поглощать/уничтожать объект —
берите `&self`. `self` (consuming) — это исключение, а не норма.

### Когда `self` (consuming) — правильный выбор

1. **Builder-паттерн.** Наш `IsDayOffBuilder::build(self)`:

   ```rust
   pub fn build(self) -> IsDayOff {
       IsDayOff {
           base_url: self.base_url.unwrap_or_else(|| BASE_URL.into()),
           country: self.country,
           // ...
       }
   }
   ```

   Билдер после сборки не нужен — все поля просто "переезжают" в готовый
   `IsDayOff`. Если бы было `&self`, пришлось бы клонировать `String` и
   остальные поля вместо перемещения. Плюс билдер — одноразовый объект:
   `self` физически не даёт вызвать `build()` дважды (переменная билдера
   становится недействительной после первого вызова).

2. **Конвертации `into_*`.**

   ```rust
   let s = String::from("hi");
   let bytes: Vec<u8> = s.into_bytes(); // s больше не используется
   ```

   Метод переиспользует ту же память под новым типом без копирования.

3. **Типобезопасные одноразовые операции (typestate).** Например,
   транзакция: `tx.commit(self)` — после коммита объект `tx` исчезает,
   компилятор не даст закоммитить дважды или использовать после коммита.
   Это гарантия на этапе компиляции, а не ручная проверка вида
   `if committed { panic!() }`, как пришлось бы в Go.

4. **`IntoIterator`.** `for x in vec { ... }` вызывает `into_iter(self)` и
   поглощает `vec`; `for x in &vec { ... }` — заимствует, `vec` остаётся
   жив.

Во всех остальных случаях (подавляющее большинство методов) — `&self`.

## 2. `Option<T>` и `if let Some(x) = ...`

`Option<T>` — enum с двумя вариантами, замена `null`/`nil`:

```rust
enum Option<T> {
    Some(T),
    None,
}
```

Ключевое отличие от указателей в Go: компилятор **не даст** использовать
`T` внутри, пока `Option` явно не "открыт".

### `if let` — сокращённая форма `match`

Пример из `build_url`:

```rust
if let Some(m) = month {
    q.append_pair("month", &format!("{m:02}"));
}
```

Разворачивается в:

```rust
match month {
    Some(m) => {
        q.append_pair("month", &format!("{m:02}"));
    }
    None => {}
}
```

`Some(m)` — это **образец (pattern)**: проверяет, что `month` — вариант
`Some`, и одновременно связывает содержимое с новой переменной `m`
(`u32`), доступной только внутри блока `{ }`. `month` снаружи остаётся
`Option<u32>` — не мутируется.

Аналог из Go — идиома "comma ok" (`if v, ok := myMap[key]; ok { ... }`),
но с важной разницей: в Go компилятор не обязывает вас всегда так делать
— можно случайно разыменовать nil-указатель и словить панику в проде. В
Rust `u32` физически недостижим, пока `Option` не распакован — ошибка
`None`-случая ловится на этапе компиляции.

В `build_url` эта конструкция использована не просто "чтобы проверить
null", а чтобы закодировать **гранулярность запроса** к API:

```rust
fn build_url(&self, year: i32, month: Option<u32>, day: Option<u32>) -> String
```

- `month: None` → запрос за год целиком.
- `month: Some, day: None` → запрос за месяц.
- `month: Some, day: Some` → запрос за конкретный день.

## 3. Borrow checker + `Drop`: почему нужен блок `{ }`

Рабочий код:

```rust
fn build_url(&self, year: i32, month: Option<u32>, day: Option<u32>) -> String {
    let mut url = reqwest::Url::parse(&self.base_url).expect("Invalid base URL")
        .join("/api/getdata").expect("invalid path");

    {
        let mut q = url.query_pairs_mut();
        q.append_pair("cc", self.country.as_str());
        q.append_pair("year", &year.to_string());
        // ...
    }

    url.into()
}
```

Без внешнего блока `{ }` компилятор выдаёт:

```
error[E0505]: cannot move out of `url` because it is borrowed
   |
   | let mut q = url.query_pairs_mut();
   |             --- borrow of `url` occurs here
...
   | url.into()
   | ^^^ move out of `url` occurs here
   | borrow might be used here, when `q` is dropped and runs the destructor
```

**Что происходит:** `url.query_pairs_mut()` возвращает `q` —
`Serializer<'_, UrlQuery<'_>>`, объект, который **держит `&mut url`
внутри себя**, пока жив. `url.into()` требует забрать `url` по значению
(move) — а сделать это, пока есть активное мутабельное заимствование,
нельзя.

**Почему обычно в Rust заимствование "не мешает" сразу после последнего
использования (non-lexical lifetimes, NLL), а тут мешает?** Потому что у
`Serializer` есть деструктор (`impl Drop`). Для типов с `Drop`
компилятор не может считать заимствование законченным сразу после
последнего явного обращения — вызов деструктора **тоже** является
использованием заимствования, и происходит он в конце области видимости
(scope). Без блока это — конец функции, то есть *после* `url.into()`.

Блок `{ }` создаёт вложенную область видимости: `q` объявлена внутри неё
→ уничтожается в конце блока → к моменту `url.into()` заимствование уже
закрыто.

**Вывод:** если тип, который вы временно держите в переменной, имеет
деструктор — учитывайте, что заимствование живёт до конца его
*области видимости*, а не до последнего использования переменной. При
конфликте — оборачивайте временную переменную в блок.

## 4. Паника vs `Result` — recoverable vs unrecoverable errors

В Go: всё возвращается как `(T, error)`, паника — редкое исключение для
действительно нештатных ситуаций. В Rust та же философия, но
формализована на уровне типов.

### Два класса ошибок

- **Recoverable (ожидаемые)** — сеть недоступна, файл не найден,
  пользователь передал невалидную строку. Для них — `Result<T, E>`,
  прямой аналог `(T, error)` в Go. Библиотека обязана вернуть это
  наружу, а не решать за вызывающий код.
- **Unrecoverable (баги/нарушенные инварианты)** — ситуации, которые *в
  принципе не должны происходить* при правильном коде: "я только что
  проверил `len() > 0`, а `first()` всё равно `None`". Здесь `panic!` /
  `unwrap()` / `expect()` уместны — это сигнал о баге в самой программе,
  а не runtime-условие для обработки.

### Проблемное место в нашем коде

```rust
let mut url = reqwest::Url::parse(&self.base_url).expect("Invalid base URL")
```

`base_url` приходит через публичный метод билдера `.base_url(String)` —
это untrusted input с точки зрения библиотеки (как аргумент любой
публичной функции в Go). Если пользователь ошибётся в строке,
`.expect(...)` уронит программу паникой — причём не сразу при вызове
`.base_url(...)`, а только при первом реальном запросе, когда вызовется
`build_url`. Это ровно тот случай, который в Go вы бы вернули как
`error` из `url.Parse`.

Экосистема Rust явно поддерживает эту интуицию — есть clippy-линты
`clippy::unwrap_used`, `clippy::expect_used`, `clippy::panic`, которые
включают именно для библиотечного кода (и разрешают в `main.rs`/тестах,
где fail-fast — нормально).

### Как это обычно чинят в билдерах

По образцу `reqwest::ClientBuilder::build() -> Result<Client, Error>`:

```rust
pub fn build(self) -> Result<IsDayOff, Error> {
    let base_url = self.base_url.unwrap_or_else(|| BASE_URL.into());
    let base_url = reqwest::Url::parse(&base_url)?; // вместо expect
    Ok(IsDayOff {
        base_url, // можно сразу хранить как Url — build_url() не парсит его заново на каждый запрос
        country: self.country,
        // ...
    })
}
```

Потребуется:
- добавить в `Error` вариант под `url::ParseError` (через `#[from]`, как
  уже сделано для `reqwest::Error`);
- сменить тип поля `base_url` в `IsDayOff` с `String` на `reqwest::Url`.

**Итог:** если ошибка может возникнуть из-за данных, которые дал
вызывающий код (сеть, парсинг пользовательского ввода) — `Result`. Если
ошибка означает баг в самой библиотеке (нарушен внутренний инвариант) —
можно `panic!`/`unwrap`/`expect`, но и то экономно.
